# AgentPulse Codex Provider

`agentpulse-provider-codex` observes Codex threads and supports approvals, atomic user-input forms, queued prompts, and common typed remote commands. It owns a schema-pinned Codex App Server and a local WebSocket proxy (Unix sockets on Unix; loopback TCP on Windows) for `codex --remote` clients. The proxy preserves the desktop fallback while allowing a phone response to return on the exact connection that owns the request.

`agentpulse-provider-codex` 观察 Codex Thread，并支持审批、原子用户输入表单、排队 Prompt 与常用类型化远程指令。它托管固定 Schema 的 Codex App Server，并为 `codex --remote` 客户端提供本地 WebSocket 代理：Unix 使用 Socket，Windows 使用回环 TCP。代理保留桌面兜底，同时让手机响应回到拥有请求的原始连接。

## Compatibility / 兼容范围

- Codex CLI: explicitly verified `0.150.1`, `0.152.0`, `0.152.1`, and `0.153.0`. A valid SemVer newer than `0.153.0` starts best-effort with a visible warning; older unknown versions and malformed output fail before runtime creation / 已明确验证 `0.150.1`、`0.152.0`、`0.152.1` 与 `0.153.0`。高于 `0.153.0` 的合法 SemVer 会在明确警告后尽力启动；未验证的旧版本与非法输出会在创建运行目录前失败。
- Platforms: Windows loopback WebSockets and Job Objects; Linux/macOS Unix sockets and process groups / Windows 回环 WebSocket 与 Job Object；Linux/macOS Unix Socket 与进程组。
- Input: explicitly configured UUIDv7 thread IDs, or ephemeral discovery of threads opened through the same managed App Server / 显式配置的 UUIDv7 Thread ID，或对同一受管 App Server 中已打开 Thread 的临时发现。
- Events: live state, agent messages, connection changes, and turn outcomes / 实时状态、Agent 消息、连接变化与 Turn 结果。
- Write-back: exact Codex approvals, atomic Plan/user-input forms, queued or steering prompts, and the common model/resume/clear/plan/control commands / 支持精确 Codex 审批、原子 Plan/用户输入表单、排队或 Steer Prompt，以及常用 model/resume/clear/plan/control 指令。

The bundled schema was generated with:

```bash
codex app-server generate-json-schema --experimental --out schemas
```

The bundled schema is the official experimental bundle generated by `0.153.0`; its SHA-256 is `b06f77062369d481a59cc70720c12b89cb9dd49c385863923262102d3ad6c978`. Existing `0.150.1` captured fixtures also validate against this bundle. Experimental API opt-in is required for the native `turn/start.collaborationMode` field. Versions newer than `0.153.0` still use this schema strictly: unknown or incompatible protocol frames fail the Provider instead of being silently ignored. Regenerate the schema, verify fixtures, and complete a real managed App Server handshake before promoting a newer version into the explicit verified set.

## Windows Runtime

Windows launches the native executable with `app-server --listen ws://127.0.0.1:0`.
The actual address is read from a complete listening line in that child's bounded
stderr stream. This avoids guessing a free upstream port. The desktop proxy
reserves its own random loopback port during configuration and requires a random
256-bit path in `remote_uri()`; requests with a browser Origin or wrong path fail.
The proxy and observer connect to the same managed App Server and share the
existing message/approval mapping. The raw Codex upstream follows Codex's local
loopback trust model: loopback is not an ACL against other local user processes.

The resolver supports a native `codex.exe` and the official npm Windows vendor
binary behind its shell shim. It never runs `codex.ps1` or modifies execution
policy. Custom wrappers require an explicit native executable. Long/Unicode
Windows runtime paths are not subject to the Unix socket length limit.

The process starts suspended, joins a private Job Object, and then runs hidden.
A root-exit watcher kills remaining descendants if App Server exits or crashes;
source stop/drop also terminates the tree and removes only its owned directory.
Windows termination is forced after WebSocket workers stop; it is not a Codex
application-level graceful shutdown. Startup failure cleans resources before
returning. Restart is explicit and fails if another listener occupies the proxy
port; it never connects desktop traffic to an unknown listener.

Proxy limits: 16 active clients, 16 MiB frame/message limit, two-second total
WebSocket handshake deadline and bounded I/O polling. Idle/malformed clients are
isolated, and stop interrupts accepted sockets, including incomplete handshakes.
The Windows version probe is bounded by `startup_timeout`. Codex 0.153.4 has been
smoke-tested for real initialization and proxy `model/list` round trips, without
starting a model Turn; the 0.153.0 bundled schema remains the compatibility baseline.

```text
cargo test -p agentpulse-provider-codex -- --test-threads=1
cargo test -p agentpulse-provider-codex installed_ -- --ignored --test-threads=1
cargo test -p agentpulse-host --test local_cli windows_serve -- --ignored
```

Installed-Codex tests need a normal user home; Host acceptance also needs a
private LAN address. They use temporary Host state and stop their managed trees.

## Runtime usage / 运行方式

```rust,no_run
use std::error::Error;

use agentpulse_bridge::RuntimeHost;
use agentpulse_core::ProviderId;
use agentpulse_provider_codex::{CodexProvider, CodexProviderConfig};

fn main() -> Result<(), Box<dyn Error>> {
    let config = CodexProviderConfig::new(
        ProviderId::new(),
        "/tmp/agentpulse-runtime",
        ["019976a4-00f0-7312-b36c-d01f9c5c06f6"],
    )?;
    let parts = CodexProvider::build(config)?;
    let remote_uri = parts.handle().remote_uri().to_owned();
    let (port, source, handle) = parts.into_parts();

    let mut host = RuntimeHost::new();
    host.register_provider(port, source)?;
    let _ = host.start()?;

    println!("connect Codex with: codex --remote {remote_uri}");
    println!("Provider health: {:?}", handle.snapshot().health());

    let _ = host.stop()?;
    Ok(())
}
```

Start RuntimeHost before connecting another client with `codex --remote <uri>`. The URI names the Provider-owned proxy, not the App Server's upstream socket. The Provider resumes every configured thread before reporting startup success. A phone-issued `/resume` additionally hydrates user/assistant history through ascending `thread/items/list` pages into this Host run's memory.

Interactions and commands are correlated entirely in runtime memory. AgentPulse adds no interaction timeout: a request stays pending until Codex resolves it or its owning item, turn, thread, connection, or Provider runtime ends. Secret form answers are discarded after write. Prompt queues are bounded to 32 items per Session, 64 KiB per item, and 1 MiB total; a restart restores neither pending interactions nor queued prompts.

Use `CodexProviderConfig::discovering` instead when the Provider must start with
no saved Thread IDs and follow `thread/started` events from a Remote TUI. That
mapping exists only for the lifetime of the Provider.

RuntimeHost 停止会关闭 WebSocket、等待读取 Worker、终止受管 App Server，并仅清理 Provider 自己创建的私有目录。实时协议或进程故障会将已跟踪 Session 标记为 `Disconnected`，并通过 `CodexProviderHandle` 暴露终态错误；恢复方式是显式停止并重新启动 RuntimeHost。

The canonical mapping and lifecycle contract is defined in the AgentPulse protocol repository's `codex-provider.md`.
